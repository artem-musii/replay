## Why WebMCP is fundamental here

REPLAY’s incident model is spatial, temporal, branched, versioned, and provenance-aware. Screen actuation can move a car or fill a field, but it cannot reliably tell an agent which branch a trajectory belongs to, whether a statement is confirmed or merely reported, which evidence supports it, or whether the human corrected the scene after the agent’s previous action. WebMCP exposes those meanings as narrow operations while the human and agent inspect the same live page.

The collaboration loop is therefore bidirectional:

```text
human UI or agent tool
  -> validate the same schema and permissions
  -> invoke the same query or canonical domain command
  -> run deterministic consistency rules where applicable
  -> human mutation: live commit + notify, then queued CAS save
  -> WebMCP mutation: isolated stage -> CAS save -> live commit + notify
       post-save abort/live conflict -> compensating CAS restore
  -> read/UI-only/rejection: render a capped session audit only
  -> return a compact, verifiable result

cancellation before primary persistence begins -> neither mutation nor audit entry
```

The UI remains complete when WebMCP is absent. WebMCP is a progressive enhancement that improves shared meaning and reliability, not a hidden second application.

### Normalized spatial round trip

Every `get_workspace_state` result has a root `coordinateSystem` object. It declares `type: "normalized-scene"` and an affine projection against the open case's `environment.bounds`, with x increasing left-to-right and y increasing top-to-bottom. Ordinary geometry inside those bounds is inclusive from 0 to 1. Schema-valid diagnostic geometry outside the configured bounds is not clamped: its coordinates remain proportional below 0 or above 1. `rotationDeg` is in degrees, and `timeMs` is in milliseconds from the reviewed interval start. Scene bounds/polygons, actor poses, trajectories, timeline-event locations, and hypothesis/proposal geometry use that output convention. Domain/UI selectors keep their internal coordinate representation unchanged; only the WebMCP projection is normalized.

When `get_workspace_state.branchId` is supplied, only the requested `scene` and `timeline` projections use that branch. Root `branchContext` and each projected section distinguish `projectedBranchId`/`branchId` from the unchanged `activeBranchId`, and `branchIsActive` makes the relationship explicit. `focus_workspace_item.branchId` uses the same branch identity for a trajectory/event selection but never dispatches `hypothesis.set-active`. `compare_hypotheses` returns the same root coordinate convention plus bounded `geometryTimingDeltas`: each item places the first requested branch and one alternative side by side, preserves complete returned keyframe IDs/times, and reports `totalCount`, `returnedCount`, and `truncated` separately for paths and events.

Every returned finite normalized x/y value can be reused directly in spatial tool inputs without rescaling, including a proportional value outside 0..1. An unchanged value from a read is preserved through a direct read → write round trip.

`propose_scene_changes` accepts 1–10 changes with no repeated `actorId`. Read the current `scene` and `timeline` sections first for actor and branch IDs, normalized geometry, and `timeline.timeRangeMs`. Use a full `trajectory-set` as complete reconstruction mode when creating or intentionally replacing a path: the first ordered keyframe is the vehicle's starting pose, the last is its final pose, and intermediate keyframes may place the vehicle at described contact or maneuvers. Those keyframes are geometry only; create or update the provisional semantic impact separately with `mark_impact_event`. All proposed geometry remains pending until a human accepts it in the visible UI.

For bounded path refinement, `trajectory-keyframe-patch` is the conservative mode. One patch identifies an actor and active branch and supplies 1–8 unique adjustments to existing **interior** keyframe IDs. Each adjustment must change at least one of x, y, or `rotationDeg`; omitted values remain unchanged. The adapter rejects missing or ambiguous trajectories, missing/duplicate keyframes, archived branches, and endpoint IDs. It expands a valid patch into the canonical complete `trajectory-set` stored in the proposal revision while preserving all keyframe IDs, all `timeMs` values, both endpoints, unmentioned coordinates/rotations, and visibility.

## Consistency scopes and interpretation

`validate_case_consistency` routes through the same deterministic projection the UI uses. `all` runs every scope; `scene` is the composite of `geometry`, `motion`, and `damage`.

- `geometry` converts normalized positions through the recorded metre calibration, checks full oriented footprints from source-labelled vehicle dimensions at reported contact, applies stated calibration uncertainty, and samples the same smooth trajectory used by playback for swept-footprint road departure.
- `motion` emits advisories for speed, acceleration, deceleration, yaw rate, heading versus travel direction, turn radius, and lateral acceleration. Thresholds are deterministic functions of the declared speed/road context, road condition, wheelbase/dimensions, and calibration.
- `integrity` surfaces weak or missing calibration/dimension sources, unsupported source claims, unsigned import, checksum/time anomalies, and other trust-review signals.
- `timeline`, `damage`, `provenance`, `completeness`, and `report` retain their narrower semantic checks.

These issues describe internal consistency with recorded inputs and declared assumptions. They do not simulate collision dynamics, certify a forensic reconstruction, prove actual speed/contact, decide fault, detect lies, or infer intent. The conflicting parking scenario deliberately contains a reported stationary account that conflicts with synthetic timestamped motion so a model can use this tool to surface the contradiction for human review without accusing the reporter of deception.

## Result contract

Imperative tools return compact structured results. A successful mutation is first evaluated against an isolated copy of the complete engine state, including history and request receipts. The adapter then awaits a version-checked `saveCase`; only after that resolves does it adopt the staged state and notify React. If cancellation or a live-version conflict occurs after the save resolves, the adapter explicitly compensates the durable write before returning. The tool promise is not transactionally coupled to browser paint.

```ts
interface WebMCPResult<T = unknown> {
  ok: boolean;
  message: string;
  caseVersion: number;
  activityId?: string;
  idempotent?: boolean;
  affectedIds: string[];
  issues: ConsistencyIssue[];
  visibleState: {
    workspaceMode: string;
    selectedItemId?: string;
  };
  data?: T;
  code?: string;
}
```

Local tool-schema rejection uses top-level `code: "INVALID_INPUT"` and has no domain error payload. A real domain failure is propagated at top level and also nested at `data.error`, for example:

```ts
{
  ok: false,
  code: "LOCKED_ITEM",
  caseVersion: 8,
  data: {
    error: {
      code: "LOCKED_ITEM",
      message: "timeline-event event-impact is locked",
      lockedItem: {
        id: "event-impact",
        type: "timeline-event",
        lockedBy: "human",
        allowedAlternatives: ["request-human-unlock", "fork-hypothesis"],
      },
    },
  },
}
```

For `VERSION_CONFLICT`, the current version is always the top-level `caseVersion` and is also available at `data.error.details.currentVersion` when the failure came from the engine. There is no `retryable` field. Other current domain codes include `IDEMPOTENCY_CONFLICT`, `HUMAN_CONFIRMATION_REQUIRED`, `AGENT_FINALIZATION_FORBIDDEN`, `FORBIDDEN_ACTION`, `NOT_FOUND`, `DUPLICATE_EVIDENCE`, and `UNSAFE_REVERT`. A rejected primary save or an unconfirmed compensation returns `PERSISTENCE_FAILED`. Unexpected thrown failures become top-level `EXECUTION_FAILED`; cancellation normally rejects with `AbortError`.

No mutation returns a full case dump. Every imperative tool sets `untrustedContentHint: true`, and text derived from users/evidence is limited to bounded projections.

Read results also fail closed when the complete serialized result envelope—including data, issues, version, and visible state—exceeds 512 KiB, returning `OUTPUT_BUDGET_EXCEEDED`. For `get_workspace_state`, request fewer sections or use a narrower targeted read; REPLAY never silently drops case content and presents an incomplete projection as complete.

The deterministic eight-section demo handler contract is additionally tested against a 32 KiB target. Workspace projections retain IDs, statuses, links, locks, exact scene keyframes, and fact/evidence provenance while omitting `changeHistory`, evidence `localBlobKey`, and immutable `snapshots[].preview` bodies. Snapshot entries expose `previewSummary`; the currently visible draft or selected snapshot remains complete in `visiblePreview`. Use `get_recent_activity` when action history is needed.

Each read samples `caseVersion` before and after assembling its projection. If the case changes, it retries once; continued churn returns `VERSION_CONFLICT`, so read data is never labelled with a version from a different case snapshot.

`get_recent_activity` projects a current `revertEligible` boolean onto every returned item without persisting it. The value comes from the live engine history, so it becomes false after reload, after a newer mutation, across an irreversible boundary, or when an undo would restore a human confirmation or finalized report. A caller may pass only the eligible item's canonical `id` as `revert_agent_action.activityId`; `requestId` remains an idempotency identity and session-only invocation IDs never authorize a revert.

Invoking a tool discloses its compact structured result to the connected Site Tools client/model service. That can include case text and metadata, but the tools do not return uploaded evidence image bytes. This external processing boundary is distinct from REPLAY's browser-local storage.

## Shared commands and human control

- A factual-mutation button and its equivalent tool call the same canonical engine command. The adapter may update presentation-only state, such as focus, report preview, or comparison, after validating canonical IDs; these UI-only operations do not impersonate factual commands. It uses the shared `saveCase` bridge while an engine mutation remains staged, never mutates canonical case arrays directly, and the workspace separately owns session-only invocation audit.
- Agent mutations set author `agent`, origin `webmcp`, and the call’s `requestId`. They are visible, attributable, focusable, and undoable when safe.
- `add_observation.sourceIds` contains only canonical active evidence or observation provenance. An agent may classify an observation as `human-statement`, `witness-statement`, `photo`, or `document` only when that list contains a compatible inspectable source: human/witness/document attribution cites an existing human-attributed observation of the same type, while photo attribution may instead cite active image evidence. `relatedIds` separately accepts active evidence, timeline events, actors, trajectories, and damage markers as context; unsupported or unknown relations are rejected, and source evidence automatically receives a backlink. An unsigned import cannot become a trusted human source because its human history is reset.
- Damage writes require at least one active evidence or observation in `sourceIds`; an unsourced marker is rejected rather than rendered as if it had provenance. Open-question `relatedIds` accept observations, actors, trajectories, timeline events, damage markers, and hypothesis branches, but reject direct evidence IDs so evidence remains attached through the observation or scene item it supports.
- Observation cards render human-readable chips for cited evidence plus event, scene, and branch context; question cards render chips for their related observations, scene/timeline items, and hypotheses. Selecting a chip focuses the corresponding workspace item, keeping provenance and model-facing IDs inspectable rather than hiding them in tool output.
- The command layer rejects `status: "confirmed"` or `humanConfirmed: true` from any agent origin. Only an explicit human UI review command can confirm a claim.
- Confirmation is bound to one exact claim revision. A substantive statement/source/source-ID/evidence/event/scene-link change, a newly linked evidence item/annotation, changing or removing a linked annotation, or deletion of linked/source evidence demotes a confirmed claim to `reported`, clears `humanConfirmed` and `confirmedAt`, and appends an explicit change-history record. A semantic no-op preserves confirmation; only a human UI action can confirm the revised claim again.
- Unsigned structured import cannot preserve human confirmations, answered-question attestations, reviewed notes, or immutable report snapshots as locally trusted state. The reset is recorded and exposed to `integrity` review; it is not cryptographic authentication or a claim that the import was malicious.
- `propose_scene_changes` can write only a proposal ledger entry. Only human/UI `proposal.adjust`, `proposal.accept`, or `proposal.reject` may decide it. Acceptance revalidates every saved baseline and lock before applying the latest revision, so failure cannot partially move the scene.
- Locks, finalized snapshots, and shared confirmed facts are enforced in the domain layer, not merely disabled in UI controls.
- `finalize_factual_report` prepares a visible form in declarative-compatible Chrome. OpenAI's current Site Tools browser does not expose declarative HTML form tools as Site Tools. ChatGPT Work or Codex may still interact with forms through ordinary browser capabilities, but those interactions are not WebMCP calls and must not operate REPLAY's human-only acknowledgement or confirmation controls. The form has no automatic submit attribute and cannot create the immutable snapshot; finalization requires the human review path.

## Version conflicts and idempotency

Every content mutation accepts `expectedVersion` and `requestId`:

1. Validate tool input. Invalid input returns `INVALID_INPUT` before the adapter is called.
2. Check cancellation, retain the validated caller intent, and translate the payload into a canonical domain command. State-derived adapter enrichment is not part of the caller intent.
3. Bind `requestId` to a compact fingerprint of tool type, actor/origin, and the full validated semantic payload; `requestId` and `expectedVersion` themselves are excluded. Revert fingerprints include the requested activity target.
4. If the same request already completed with the same fingerprint, return the exact in-memory receipt with `idempotent: true` without requiring the stale `expectedVersion`, honoring a mutation pause, or performing another save. After reload, persisted activity synthesizes an idempotent response with the original activity ID, activity `caseVersion`, summary, and affected IDs. Reusing the ID for a different intent returns `IDEMPOTENCY_CONFLICT` with no mutation. Legacy activity without a fingerprint retains action-type-only compatibility.
5. If a new request has `expectedVersion !== caseVersion`, return `VERSION_CONFLICT` with no canonical state/activity change; the noncancelled failed call can appear in session audit.
6. Validate and reduce the command against an isolated engine copy, including its activity, history, and receipt state.
7. Await the bridge's durable compare-and-swap save against the live baseline version. A rejected primary save occurs before live commit and is never compensated.
8. Commit and notify subscribers only if the live engine still matches the staged baseline. Cancellation or a live conflict after a resolved save first triggers an explicit compensation save.
9. Reveal affected IDs and return the compact result with freshly read visible-state metadata.

The engine and Dexie are not one physical transaction. Staging plus durable compare-and-swap gives normal success and rejected-primary-save paths all-or-nothing live/durable behavior, while compensation reconciles a resolved save followed by cancellation or a live conflict. If that compensation fails, the adapter cannot guarantee cross-layer atomicity: it leaves the live mutation uncommitted, returns `PERSISTENCE_FAILED`, and retains the failure in session audit so durable recovery is explicit. Exact receipts remain in memory; persisted activity stores the fingerprint and enough receipt metadata to prevent replay after reload, but not a separate copy of the full original result payload.

An agent receiving a conflict should reread the smallest necessary state—usually recent activity plus the affected section—and decide again. It must not overwrite the human’s newer correction. Human UI corrections that directly replace eligible agent work can be durably classified `human-override` with the overridden agent activity ID, so both records remain inspectable.

## Lifecycle and cancellation

Register with the current API only after hydration:

```ts
await document.modelContext.registerTool(tool, {
  signal: lifecycleController.signal,
});
```

- One lifecycle controller owns each deterministic registration group (base, scene, facts, hypothesis, report).
- Abort the group when its meaningful state disappears or the workspace unmounts.
- Do not churn registrations when selection or other minor state changes.
- The separate `execute(_input, { signal })` signal is checked before adapter and engine work; fake-adapter tests also cover in-flight rejection and cleanup.
- Cancellation before primary persistence begins produces no domain mutation, persistence write, version increment, canonical activity, or session invocation audit. Cancellation while the primary save is pending waits for its outcome because Dexie does not accept the invocation signal. If the save resolves, the adapter compensates it before rejecting with `AbortError`; if compensation fails, the more actionable `PERSISTENCE_FAILED` result is returned and audited.

## Prompt-injection boundary

Evidence notes, imported statements, filenames, witness text, and agent-authored hypotheses are case **data**, never instructions. Tools:

- use fixed developer-owned descriptions and allowlisted schemas;
- resolve opaque IDs instead of executing text;
- never interpret evidence text as a command or interpolate it into executable HTML/SVG;
- mark read outputs containing that content with `untrustedContentHint: true`;
- do not expose whole-case deletion, external sharing/sending, third-party evidence upload, fault determination, or automatic finalization tools.
